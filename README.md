## Overview

**Commercial Smart Facility & Sustainability Manager** is an airport-focused facility-operations prototype built for Track 2. It ingests simulated high-frequency IoT telemetry from an airport restroom environment, detects operational incidents in real time, quantifies water impact, assigns a deterministic priority, and automatically routes the correct facility team via an auto-generated maintenance ticket — all surfaced on a live command-center dashboard.

The system models a **high-footfall airport environment**, where restroom and facility telemetry (water flow, flush activity, occupancy, and sensor health) is continuously monitored, evaluated, and acted on without manual inspection rounds or complaint-driven maintenance.

### Core Workflow

```
Telemetry → Detection → Impact → Priority → Dispatch → Maintenance Ticket → Command Center
```

### What This Prototype Demonstrates

| Capability | Description |
|---|---|
| 💧 Continuous water-leak detection | Deterministic rule engine flags sustained, uncorrelated water flow |
| 📉 Water-loss estimation | Quantifies wastage from flow rate × incident duration |
| 🧼 Usage-based cleaning thresholds | Cleaning need derived from actual flush/usage events, not occupancy |
| 📡 Sensor health monitoring | Tracks ONLINE / OFFLINE / FAULT / recovery states |
| 🚨 Deterministic incident prioritization | LOW / MEDIUM / HIGH / CRITICAL, explainable by design |
| 🛠️ Automatic maintenance routing | Incidents mapped to the correct facility team |
| 🎫 Duplicate-safe ticket creation | No repeat tickets for the same active incident |
| 🖥️ Airport command-center dashboard | Live operational view for facility managers |
| 🔁 Deterministic telemetry simulator | Reproducible, scenario-based synthetic test data |

> No physical IoT hardware is required to run this prototype — all telemetry is generated by the included deterministic simulator.

## Quick Start

Run each of the following in a **separate terminal**, in order.

```bash
# Terminal 1 — Backend API
cd backend
npm install
npm start
```

```bash
# Terminal 2 — Frontend dashboard
cd frontend
npm install
npm run dev
```

```bash
# Terminal 3 — Telemetry simulator
# Run from the repository's simulator entry point
node simulator.js
```

Then open the frontend URL printed by Vite in your browser.

| Service | Default URL |
|---|---|
| Backend API | `http://localhost:3000` |
| Frontend dashboard | `http://localhost:5173` (Vite will confirm the exact port) |

## Running the Telemetry Simulator

The simulator generates **deterministic** telemetry so demos and tests are reproducible.

**Supported scenarios:**

| Scenario | Behavior |
|---|---|
| `NORMAL` | Baseline operation, no incident |
| `HIGH_USAGE` | Elevated flush/occupancy traffic |
| `LEAK` | Sustained flow with low/zero legitimate usage |
| `CLEANING_THRESHOLD` | Usage accumulation crosses the cleaning trigger |
| `SENSOR_OFFLINE` | Sensor stops reporting / goes stale |
| `RECOVERY` | Condition clears and returns to normal |

```bash
node simulator.js
```

> If the final repository uses a different simulator entry file, use the corresponding script documented beside that file.

**Simulator limit:** capped at **500 telemetry records per run** so a demonstration run stops automatically. This is a per-run limit only — the database can retain more than 500 records across multiple runs.

## Detection Logic

### 💧 Continuous Water Leak
A leak is detected from **sustained elevated water flow** combined with operational context — such as occupancy/usage conditions — and **persistence over time**, not from a single anomalous reading.

### 📉 Water Impact
Estimated wastage is calculated from the observed flow rate and incident duration:

```
Estimated Water Loss = Flow Rate × Duration
Example: 12.4 L/min × 42 min ≈ 520 L
```

### 🧼 Cleaning Threshold
Cleaning requirements are derived from **actual restroom usage / flush activity**, not from treating instantaneous occupancy as completed usage.

### 📡 Sensor Health
Sensor health tracks telemetry/sensor operational status, including `OFFLINE` and `RECOVERY` states.

### 🚨 Priority
Priority is **deterministic** — never LLM-decided — and based on:

- Incident severity
- Persistence / duration
- Water impact
- Occupancy / traffic context
- Sensor health

**Levels:** `LOW` · `MEDIUM` · `HIGH` · `CRITICAL`

### 🛠️ Dispatch

| Incident Type | Routed To |
|---|---|
| `WATER_LEAK` | Facilities / Plumbing Maintenance |
| `CLEANING_THRESHOLD` | Cleaning |
| `SENSOR_OFFLINE` | Maintenance |

## Data & Reliability Approach

The core detection, impact calculation, prioritization, and dispatch logic is **fully deterministic**. This makes the prototype:

- ✅ Reproducible
- ✅ Explainable
- ✅ Easy to test
- ✅ Independent of an LLM for critical operational decisions

**AI/LLM functionality is not required for the core incident pipeline.** Where generative AI is used elsewhere in the project, it is additive only (explanations, summaries, recommendations) and never the sole authority for detecting an incident.
